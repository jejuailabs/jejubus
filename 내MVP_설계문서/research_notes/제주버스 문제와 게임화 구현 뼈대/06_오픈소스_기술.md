## 1. 교통 엔진과 GTFS 도구: GitHub 숏리스트

### Takeaway
MVP에 서버형 엔진(OTP, OneBusAway, MOTIS, Valhalla 등)은 넣지 않는다. 전부 상시 서버가 필요하고, 제주 공개 GTFS도 찾지 못했기 때문이다. 지금 바로 쓸 만한 것은 라이브러리와 오프라인 도구(pfaedle, gtfs-validator, Turf, H3, gtfs-realtime-bindings)이고, GTFS를 직접 만든 뒤에야 MOTIS가 다음 후보가 된다.

보조 근거:
- OTP 필요 메모리는 데이터에 따라 1 GB 미만에서 100 GB 초과까지 다르고, 핀란드 전체는 10 GB 남짓, 독일은 95 GB다 — [OTP System Requirements](https://docs.opentripplanner.org/en/latest/System-Requirements/)
- MOTIS는 OSM `osm.pbf` 1개, GTFS·NeTEx, GTFS-RT·SIRI를 입력으로 받고, README에서 "low memory usage"를 내세운다. 벤치마크 수치가 아닌 자체 주장이다 — [MOTIS README](https://github.com/motis-project/motis)
- TransitClock은 GTFS-RT 차량 위치를 입력받아 GTFS-RT 도착예측을 내는 구조다. 다만 이 설명의 출처는 제3자 미러였다 — [검색 결과의 TransitClock 소개](https://dr.molodetz.nl/_proxy/https/thetransitclock.github.io/)
- 전 세계 피드 카탈로그인 Mobility Database는 99개국 이상 6,000개 이상 피드를 담지만, 검색 결과에 한국 피드는 나오지 않았다 — [Mobility Database](https://mobilitydatabase.org/about)

### Inferences
- 제주 인구 규모의 OTP·MOTIS 그래프는 독일 수치보다 훨씬 작을 것이므로 소형 VM으로 가능해 보인다. 다만 측정값이 아니라 추정이다.
- AGPL·GPL 프로젝트(Catenary, digitransit, bus-tracker-2)는 코드를 복사하지 말고 화면 아이디어만 참고한다. 오프라인 GPL CLI(pfaedle, LOOM)는 도구로 실행만 하므로 앱 코드까지 GPL이 전파될 위험은 낮아 보인다. 법률 판단은 아니다.
- 사용자가 적은 "transit-tracker"는 동명 프로젝트가 여럿이라, 가장 스타가 많은 EastsideUrbanism 저장소로 해석했다. 이 프로젝트는 하드웨어 전광판이지 앱 백엔드가 아니다.

### Gaps
- Valhalla, transitland-lib, EastsideUrbanism/transit-tracker의 정확한 라이선스 원문을 끝까지 확인하지 못했다.
- MOTIS의 제주 규모 메모리 수치는 찾지 못했다.
- 상시 VM 월 비용은 조사하지 않았다.

## 2. 한국·제주 관련 저장소와 데이터 소스

### Inferences
- 제주 GTFS를 내려받아 시작하는 경로는 막혀 있다고 보고, TAGO에서 자체 경량 GTFS를 만드는 것을 기본 경로로 잡는 편이 안전하다.
- 라이선스가 없는 저장소는 기본적으로 저작권이 유보되어 있으므로 코드를 가져오지 않는다.

## 3. 버스 도착시간 예측(ETA): 제주 TAGO 위치를 쌓아 개선할 수 있는가

### Takeaway
가능하다. 다만 시작은 LSTM이나 GNN이 아니라 "구간별, 시간대별 소요시간 중앙값 + 앞차 보정"이다. TAGO 위치 응답에는 정류장 순번이 있어 정류장 통과 이벤트를 만들 수 있고, 수천 운행이 쌓이면 효과가 포화되는 경향도 있어, 작은 팀에 맞는 규모다. 딥러닝은 데이터가 몇 달 쌓이고 단순 방법의 한계가 측정된 뒤에 검토한다.

### Cited Findings

**논문**
- BusTime(더블린 GPS, 500~4,311 운행): LSTM, 커널 회귀, k-NN, delay, 가법 모델을 비교했다. 정확도 순위는 LSTM, KR, k-NN, delay, additive였다. 1,000 운행 정류장 기준 MAE는 LSTM 약 86초, KR 약 216초였다. 약 2,000 운행을 넘으면 개선폭이 작아졌고, 전체 4,311 운행에서 KR은 약 189초였다. LSTM은 1,000, 3,000 운행에서만 실험됐고, 하이퍼파라미터 튜닝 시간은 학습시간에서 제외됐다 — [Liu, Sun, Wang 2020](https://ar5iv.labs.arxiv.org/html/2003.10373)
- 자율주행 셔틀 6개 지역 약 6.4만 건 주행 관측: 체류시간(dwell)이 저속, 저교통 환경의 핵심 오차 요인이었다. 주행시간은 대부분 지역에서 단순 모델이 이미 변동을 대부분 설명했다. 평균 회귀 대비 누적 주행시간 오차 개선은 15~32%, 체류시간 오차 개선은 26~61%였다. RF-GCN은 데이터가 많을 때만 우세했고, 데이터가 적은 Graz에서는 어떤 모델도 평균 회귀를 이기지 못했다 — [Schmidt, Tygesen, Rodrigues](https://arxiv.org/html/2401.05322v2)
- 대규모 데이터가 있으면 ANN이 조금 낫고 데이터가 없으면 칼만 필터가 유리하다는 결론의 비교 연구가 있다. 초록 요약 수준으로만 확인했다 — [TRID 1288350](https://trid.trb.org/View/1288350)
- GNN 사례: GNN + LSTM으로 GTFS 정적 구조와 실시간 데이터를 결합([Gramaglia & Bacciu](https://arpi.unipi.it/handle/11568/1313107)), GNN + Spacetimeformer를 뉴욕 MTA에 적용([Gallage 외 2025](https://dl.lib.uom.lk/handle/123/24421)), 벨루오리존치 버스에 GNN + RNN 적용([피사대 석사논문 2025](https://etd.adm.unipi.it/t/etd-05142025-105928)).
- 칼만 필터가 과거 주·일·시간 데이터로 주행시간과 체류시간을 나누어 다루고, 몰림(bunching)을 예상할 수 있게 한다는 벤더 사례가 있다. 벤더 블로그이므로 성과 주장은 그대로 믿지 않는다 — [Camsys](https://camsys.com/blog/a-pilot-to-enhance-real-time-bus-predictions-for-metro-transit)

### Inferences

**권장 파이프라인 (노선 개정 때만 실행, 서버 비용 0원)**
1. TAGO `getRouteAcctoThrghSttnList`로 노선별 정류장 순서를 내려받는다.
2. `stops.txt`, `routes.txt`, `trips.txt`, `stop_times.txt`(더미 시각)로 최소 GTFS를 만든다.
3. 대한민국 OSM 추출본 + pfaedle로 `shapes.txt`를 생성한다.
4. 자동 검사: 정류장과 선형 거리, 직선거리 대비 우회율, 왕복 차이. 임계값을 넘으면 실패로 표시한다.
5. 실패 노선은 OSRM 라우팅, 그다음 카카오로 비교하고, 필요하면 사람이 수정한다.
6. GeoJSON을 간소화(Turf)해 정적 파일로 배포한다. 노선당 파일 하나.
7. 원시 GPS가 쌓이면 여러 운행을 겹쳐 선형을 검증한다. 60초 간격 단일 운행은 Meili 권장 밀도보다 성기므로 여러 운행 합성이 필요하다.

- 게임 지도에는 맵매칭 자체가 필요 없을 수 있다. 진행도를 `nodeord / 전체 정류장 수`로 표시하면 도식 노선 위에 바로 올라간다.
- OSM에서 파생된 선형은 ODbL 표기 의무가 생기고, 데이터베이스 공유 조건이 따를 수 있다. 공개 전 표기를 넣고 범위를 검토한다.
- 현재 카카오 키를 펀제주와 공유하므로 대량 선형 생성에 쓰면 다른 서비스에 영향이 간다. 소량으로 제한하거나 별도 앱을 쓴다.

### Inferences
- **불편 제보 분류**: 첫 200~500건은 기존 LLM API로 구조화 분류(유형, 노선, 정류장, 긴급도)를 하고, 사람이 확인해 정답 데이터를 만든다. 데이터가 쌓이면 임베딩 + 로지스틱 회귀로 비용을 줄인다. 공개 한국어 제보 분류 모델은 찾지 못했으므로 직접 데이터가 가장 큰 자산이다.
- **번역**: 공식 UI 문구는 미리 번역해 정적 저장하고, 사용자 글은 API로 온디맨드 번역 후 캐시한다. 앱이 이미 4개 언어(i18n)를 지원하므로 오픈 모델을 직접 호스팅할 이유가 약하다. 정류장명 같은 고유명사는 공식 다국어 사전을 우선하고 기계번역을 쓰지 않는다.
- **제주어 모델**: 안내 품질 기능이 아니라 캐릭터 말투 같은 재미 요소로만 쓴다.
- **이미지**: 런타임 생성은 제외한다. 제작 시점에 FLUX 계열로 에셋을 만들어 정적 파일로 넣는다. 수업 도구(Higgsfield 등) 사용도 가능하나 이 문서 범위 밖이다.

### Gaps
- 라이선스 표기가 없는 모델(ko-sroberta, HY-MT 카드 등)은 Hub 태그만으로 확정하지 못했다.
- 한국어 불편 제보 분류 공개 모델·데이터셋은 HF 검색에서 찾지 못했다. 검색어 한계일 수 있고 AIHub는 확인하지 못했다.
- 각 번역 모델의 제주 교통 문장 품질은 실측하지 않았다. 50문장 평가가 필요하다.
- 소형 LLM의 실제 한국어 품질과 CPU 속도는 측정하지 못했다.

## 8. 권장 기술 뼈대

### Takeaway
"Vercel은 앱 서빙, 별도 수집기는 데이터 축적, 로컬 배치는 무거운 작업"으로 3분할한다. 현재 구조를 유지한 채, 이번에 추가할 것은 수집기, 노선 선형 파일, 게임 레이어 세 가지다.

**프로젝트 규칙과의 충돌**: [CLAUDE.md](file:///C:/Users/na/Desktop/ai%20힉스필드%20수업/jejubus/내MVP_설계문서/CLAUDE.md) 1항은 자체 ETA를 추가 요청 전 제외로 두고, 6항은 AI가 도착 시각을 계산하지 않는다고 정한다. 8항은 별도 과금이 생기는 작업 전 구체적 승인을 요구한다. 따라서 3단계 이후 자체 ETA는 사용자의 명시적 범위 확장 없이는 화면에 공개하지 않고, 그 전까지는 TAGO `arrtime`과 나란히 비교하는 내부 측정으로만 둔다. 공개하더라도 공식 정보와 자체 추정을 구분해 표시한다. 수집기, 객체 저장소, Vercel Pro, LLM 호출은 비용 0원으로 보이더라도 공급자, 과금 기준, 무료 한도, 초과 조건을 설명하고 승인받은 뒤 켠다.

**지금 하지 않을 것**: OTP, OneBusAway, TransitClock 운영, GNN·LSTM 학습, 런타임 이미지 생성, Vercel 내 모델 직접 추론, Phaser 전체 게임, Mapbox 유료 스택, NLLB·EXAONE·Hunyuan 사용.

**가장 먼저 검증할 3가지**: (1) TAGO 위치 실제 갱신 주기, (2) 제주 OSM으로 pfaedle 선형 품질, (3) 카카오 경로 결과 저장 허용 여부.

### Gaps
- 위 비용은 트래픽 예측 없이 산정했다. 월 사용자 수가 정해지면 다시 계산해야 한다.
- 단계별 일정은 인력 조건을 모른 채 순서만 제안한 것이다.
